# Backup & Recovery Runbook

This document is the operator-facing guide to backing up and restoring the
Eagle Eye application. It covers **what** is in scope, **how** to run the
provided scripts, and **what to do** when something goes wrong.

The on-disk scripts live in [`scripts/backup/`](../scripts/backup/README.md).
Read that README first if you just want to run a backup; this document is
the longer, "why" reference.

---

## 1. Scope

### 1.1 What IS backed up by these scripts

| Asset | Mechanism | Notes |
| --- | --- | --- |
| PostgreSQL data (the `app` database) | `pg_dump` logical backup (custom format, `-Fc`) | Captures all schemas, data, and the `alembic_version` row |
| Local media uploads (`uploads/` directory) | `tar -czf` archive | Only used when `MEDIA_STORAGE_BACKEND=local` |
| Secrets in environment | _Not backed up here_ | Stored in `.env` (or the deployment's secret store). Backups are the responsibility of the secret-management process. |

### 1.2 What is NOT in scope

- **Object storage (S3 / R2 / B2 / MinIO) backups.** When
  `MEDIA_STORAGE_BACKEND=s3`, uploaded media lives in the provider's bucket
  and the app never re-downloads it. Backup and versioning of that data is
  the storage provider's responsibility (enable bucket versioning, lifecycle
  rules, and provider-side encryption at minimum). The application code
  does not and must not pull objects back through itself.
- **Docker volume snapshots.** These scripts are deliberately file-level
  (`pg_dump`, `tar`) so the database is consistent regardless of where the
  Postgres data directory lives. A volume-level snapshot taken while
  Postgres is running risks a torn write. If you want physical backups in
  addition, use `pg_basebackup` against a quiesced instance.
- **Generated front-end client (`backend/app/frontend/`).** It is in
  `.gitignore` and regenerated by `scripts/generate-client.sh` and the
  pre-commit hook. There is no value in backing it up.
- **Test artifacts** (`test-results/`, `playwright-report/`, etc.). Already
  ignored.
- **The application binary / container image.** Re-pull from the registry
  (`ghcr.io/...`) as part of recovery; the image is reproducible from the
  repository.

### 1.3 What's not yet automated

Backups are **run by an operator** (or by an external scheduler that wraps
the scripts). This implementation does not add a cron job, systemd timer,
or CI workflow — the operator chooses the schedule and the off-host
destination. Section 7 sketches a recommended schedule.

## 2. Configuration and prerequisites

### 2.1 Required tools

| Tool | Used by | Notes |
| --- | --- | --- |
| `pg_dump` | `db-backup.sh` | Provided by the `postgres:18` image or any PostgreSQL client package |
| `pg_restore` | `db-restore.sh`, `db-verify.sh` | Same |
| `psql` | `db-restore.sh`, `db-verify.sh` | Same |
| `createdb`, `dropdb` | `db-restore.sh`, `db-verify.sh` | Same |
| `tar` | `media-backup.sh`, `media-restore.sh` | GNU tar recommended; ships with every Linux distribution and the `postgres:18` image |

The scripts **fail loudly** (non-zero exit) if any required tool is
missing. They do not attempt to install packages.

### 2.2 Environment variables

The scripts read only non-secret variables. Secrets must be supplied out of
band.

| Variable | Default | Used by | Purpose |
| --- | --- | --- | --- |
| `POSTGRES_DB` | `app` | `db-backup.sh`, `db-restore.sh` | Live application DB name; also the DB the restore script refuses to touch |
| `POSTGRES_USER` | `postgres` | all DB scripts | Role to connect as |
| `POSTGRES_HOST` | `localhost` | all DB scripts | DB host |
| `POSTGRES_PORT` | `5432` | all DB scripts | DB port |
| `MEDIA_STORAGE_LOCAL_DIR` | `uploads` | `media-backup.sh`, `media-restore.sh` | Source / live media directory |
| `ALLOW_LIVE_DB_RESTORE` | _unset_ | `db-restore.sh` | Must equal `1` to allow `--force` against the live app DB |
| `ALLOW_LIVE_MEDIA_RESTORE` | _unset_ | `media-restore.sh` | Must equal `1` to allow `--force` extraction into the live media dir |

The password is read by `pg_dump` / `psql` from:

1. A `~/.pgpass` entry (recommended for unattended use)
2. The `PGPASSWORD` environment variable
3. The compose service's `POSTGRES_PASSWORD` (when running inside the `db` container)

The backup scripts **never print** the password, never read it from
`.env`, and never write it to logs.

### 2.3 What the operator decides

These decisions are intentionally outside the scripts. Document the answers
in your runbook.

- Where backups are written (default: `backups/db/`, `backups/media/`).
- How they are moved off-host (rsync, restic, `aws s3 cp`, BorgBackup, etc.).
- How long they are retained (see Section 7).
- How the DB password is provided to the backup job.

## 3. Database backup

### 3.1 What it does

`scripts/backup/db-backup.sh` invokes `pg_dump` against the configured
database and writes a single custom-format archive:

```
backups/db/eagle-eye-db-<UTC-YYYYMMDDTHHMMSSZ>.dump
```

The custom format is already compressed; the script does not double-gzip
the output.

### 3.2 Running it

From the repository root, with the DB reachable at `localhost:5432`:

```bash
bash scripts/backup/db-backup.sh
```

From inside the compose `db` service (recommended in dev — no need to
publish the DB port to the host):

```bash
docker compose exec -T db bash /app/scripts/backup/db-backup.sh
```

(To do this you must mount `scripts/backup/` into the `db` service. The
shipped `compose.yml` does not do that; add a bind mount in your
environment or copy the script into the container once.)

### 3.3 Useful flags

| Flag | Effect |
| --- | --- |
| `--db NAME` | Override `POSTGRES_DB` for this run |
| `--user NAME` | Override `POSTGRES_USER` |
| `--host NAME` / `--port N` | Override host / port |
| `--output-dir DIR` | Override the output directory |
| `--name PREFIX` | Override the file prefix (default `eagle-eye-db`) |
| `--force` | Allow overwriting an existing file |
| `--dry-run` | Print resolved config and exit without contacting the DB |

### 3.4 Confirming success

A successful run prints the destination file path, the byte count, and
exits `0`. The artifact is `chmod 600`'d.

**Treat a zero-byte file or any non-zero exit code as a failed backup and
trigger the alert path**, even if `pg_dump` did not print an error. (The
script already removes a zero-byte artifact; the absence of the file is
the signal.)

## 4. Database restore

### 4.1 Two-step process

A restore is dangerous. The intended flow is:

1. **Inspect the archive** (no DB changes).
2. **Verify it** with `db-verify.sh` into a throwaway DB (no live DB
   changes).
3. **Restore for real** only when the inspection and verification pass.

### 4.2 Inspecting

```bash
bash scripts/backup/db-restore.sh --archive backups/db/eagle-eye-db-<TS>.dump --list
```

`--list` prints the archive's table-of-contents and exits. This works
without a target DB and never touches the live database. (The default mode
of `db-restore.sh` is now **restore**, not list — see Section 4.4 — so
`--list` must be passed explicitly to do a no-DB inspection.)

### 4.3 Verifying

See [Section 6](#6-verifying-a-backup) below. `db-verify.sh` restores the
archive into a uniquely-named temporary DB, runs sanity queries, and
drops the DB on exit.

### 4.4 Restoring for real

Pick a target database name that is **not** the live app DB (`app`):

```bash
createdb -h localhost -U postgres eagle_eye_test_restore
bash scripts/backup/db-restore.sh \
    --archive backups/db/eagle-eye-db-<TS>.dump \
    --target-db eagle_eye_test_restore
```

To restore **over** the target DB (destructive):

```bash
bash scripts/backup/db-restore.sh \
    --archive backups/db/eagle-eye-db-<TS>.dump \
    --target-db eagle_eye_test_restore \
    --force
```

To restore into the **live** app DB, every safeguard must be lifted:

```bash
ALLOW_LIVE_DB_RESTORE=1 \
bash scripts/backup/db-restore.sh \
    --archive backups/db/eagle-eye-db-<TS>.dump \
    --target-db app \
    --force
```

The script will refuse the operation unless both `--force` and
`ALLOW_LIVE_DB_RESTORE=1` are set, and it will print a loud warning before
touching the live DB. This is by design.

> **Default mode changed.** Earlier versions of `db-restore.sh` defaulted
> to "list only" and required no flag to perform a restore. The script
> now defaults to **restore** (so the flag is `list`, not `restore`).
> Operators upgrading must remove any flag they were using to force a
> restore, and add `--list` to scripts that previously relied on the
> implicit list mode.

### 4.5 After a restore

1. Re-run the application migrations? **No.** `pg_dump` includes
   `alembic_version` and the current schema; running `alembic upgrade
   head` after a restore is a no-op but harmless. The compose
   `prestart.sh` does this automatically on the next container start.
2. Re-seed initial data? Only if the restored database was completely
   empty. `pg_dump` of an existing DB includes `initial_data`-equivalent
   rows, so the normal `prestart.sh` skip-if-present logic applies.
3. Verify the application can boot and login.

## 5. Media backup and restore

### 5.1 Local media

`scripts/backup/media-backup.sh` archives `uploads/` (or whichever
directory `MEDIA_STORAGE_LOCAL_DIR` points to) into:

```
backups/media/eagle-eye-media-<UTC-YYYYMMDDTHHMMSSZ>.tar.gz
```

Restore with `media-restore.sh` into a different directory by default;
extract into the live `uploads/` only after explicit opt-in (`--force` and
`ALLOW_LIVE_MEDIA_RESTORE=1`).

### 5.2 S3-compatible storage

When `MEDIA_STORAGE_BACKEND=s3`, the application does **not** download
objects to itself; backups are a bucket-level concern:

1. **Enable bucket versioning.** This protects against accidental
   deletion by a user or process.
2. **Enable server-side encryption** (SSE-S3, SSE-KMS, or equivalent).
3. **Set a lifecycle policy** to transition older objects to cheaper
   storage classes or to expire deleted-tombstoned objects.
4. **Cross-region replication** is recommended for DR; replicate to a
   different region and account.
5. **Periodically test restore** by spinning up a test bucket and
   verifying object accessibility.

The application never re-uploads from a local file system in S3 mode;
object keys are immutable references, and rebuilding media from the
application's own upload endpoint is not a valid recovery strategy.

## 6. Verifying a backup

`db-verify.sh` is the recommended gate before relying on an archive. It:

1. Checks the archive has a `PGDMP` header.
2. Runs `pg_restore --list` to confirm it's well-formed.
3. Creates a uniquely-named temp DB.
4. Restores the archive into it (`--exit-on-error`).
5. Counts public tables and reads `alembic_version` (if present).
6. Drops the temp DB (unless `--keep-on-failure`).

Usage:

```bash
bash scripts/backup/db-verify.sh \
    --archive backups/db/eagle-eye-db-<TS>.dump
```

With the expected Alembic head:

```bash
HEAD="$(uv run --project backend alembic heads 2>/dev/null \
    | awk '{print $1}' | head -1)"
bash scripts/backup/db-verify.sh \
    --archive backups/db/eagle-eye-db-<TS>.dump \
    --expect-head "$HEAD"
```

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | All checks passed |
| `2` | Bad arguments / missing archive |
| `3` | Required tools unavailable |
| `4` | Restore or sanity check failed |

**Do not claim a backup is verified unless this script exits 0.** The
script never reports success when the required tools are missing.

## 7. Retention and off-host storage

Recommended retention (adjust to your risk profile):

| Tier | Frequency | Keep for |
| --- | --- | --- |
| Daily | every 24h | 7 days |
| Weekly | every Sunday | 4 weeks |
| Monthly | first of the month | 6 months |
| Off-machine copy | every backup | indefinite (until purged) |

Storage requirements (rough):

- A logical dump of a small / medium Postgres database is in the low-MB
  range; the `uploads/` archive depends entirely on how much media the
  deployment has accumulated.
- Use a separate account / region / bucket for the off-machine copy so a
  compromise of the production host cannot reach the backup.

Use a tool that provides content-addressable storage and encryption
(restic, BorgBackup, `aws s3 cp` with SSE-KMS, etc.) for the off-host
copy. Do not store backup artifacts in the same volume as the database
data — a volume-level failure takes both.

## 8. Disaster recovery

In order of preference:

1. **Restoring into a fresh staging environment.** Preferred. Pull the
   latest backup, run `db-verify.sh`, then `db-restore.sh` into a clean
   staging DB. Update DNS or smoke-test URLs.
2. **Restoring into the live DB.** Acceptable after a destructive event
   (e.g. accidental `DROP TABLE`). Always run `db-verify.sh` first
   (against a copy, not the live DB), then promote.
3. **Reconstructing from off-host snapshots.** Last resort. Restore the
   off-host copy to a new host, re-deploy, re-point DNS.

### 8.1 Decision flow

```
Is the live DB intact and consistent?
  ├─ yes → no restore needed; investigate the original issue
  └─ no  ↓
Is there a recent verified dump?
  ├─ yes → restore per Section 4 into a new DB, verify, then promote
  └─ no  ↓
Is the live host available for forensic capture?
  ├─ yes → snapshot first, then escalate to off-host backups
  └─ no  → restore from off-host copy to a new host
```

### 8.2 RTO / RPO guidance

This implementation does not measure RTO (recovery time objective) or
RPO (recovery point objective) for you. As a rule of thumb:

- **RPO** is bounded by your backup frequency and how quickly off-host
  copies land. Daily backups with immediate off-host replication give a
  24h RPO at worst.
- **RTO** is bounded by how fast you can run the scripts, redeploy the
  application, and re-point DNS / proxies. For a single-host deployment
  expect tens of minutes.

## 9. Security

### 9.1 Secrets in backups

A logical Postgres dump **contains**:

- The `users` table, including password **hashes** (bcrypt) and email
  addresses.
- The `contact_message` table (name, email, message body).
- Any data the application stores (article drafts, comments, etc.).

Treat backup artifacts with the same care as the live database:

- `chmod 600` (the scripts do this).
- Encrypt at rest in the off-host destination (SSE-KMS, restic, etc.).
- Restrict the IAM / filesystem permissions to operators who need them.
- **Never commit backup artifacts to git.** The `.gitignore` blocks
  `*.dump`, `*.dump.gz`, `*.sql.gz`, `*.bak`, and `/backups/`.

### 9.2 Transport

- Backups that travel over the network (off-host copy) must use TLS
  (S3, restic over SSH / TLS, rsync over SSH, etc.).
- Don't run backup jobs on a host whose outbound traffic is unmonitored;
  a compromised host exfiltrating dumps is a high-impact event.

### 9.3 Pre-commit safety net

The repository's pre-commit configuration includes
`scripts/guard-secrets.sh`, which blocks obvious secret patterns in
tracked files. The new backup scripts intentionally avoid printing or
embedding credentials so the guard never trips on them.

## 10. Troubleshooting

### `pg_dump: error: connection to server ... failed`

The DB is unreachable. Check:

- Is the `db` service running? `docker compose ps`
- Is the port published to the host? `docker compose port db 5432`
- Is `PGPASSWORD` set, or is there a `~/.pgpass` entry?

### `db-verify.sh: required tool not in PATH: createdb`

The PostgreSQL client tools are not installed on the host you ran the
script on. Either install them (`postgresql-client` on Debian/Ubuntu,
`postgresql` on Alpine, etc.) or run the script inside the `db` service
where the tools are part of the image.

### `db-restore.sh: refusing to restore into the live app DB (app) without --force`

This is the safeguard working. Either:

- Pick a different `--target-db`, or
- Add `--force` and `ALLOW_LIVE_DB_RESTORE=1` to acknowledge the
  destructive action.

### The backup file is 0 bytes or missing

`db-backup.sh` removes a zero-byte file automatically. The script
exits non-zero. Investigate:

- Free disk space in the output directory.
- `pg_dump` stderr (the script does not capture it into a log file —
  redirect the run: `bash scripts/backup/db-backup.sh 2>backup.log`).
- Authentication: if `pg_dump` cannot authenticate it may still produce
  an empty file in some configurations.

### `pg_restore: error: could not execute query`

A schema / data mismatch between the dump and the target cluster (often
a different PostgreSQL major version). Either:

- Restore into a server with a matching major version, or
- Re-dump from a server with the target's major version.

### `media-restore.sh: refusing to extract into the live media dir`

The safeguard. Either:

- Pass `--target-dir` to extract somewhere else, or
- Add `--force` and `ALLOW_LIVE_MEDIA_RESTORE=1` to acknowledge the
  overwrite.
